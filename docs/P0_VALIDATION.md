# P0: Desktop probe and validation

Status: **P0 feasibility demonstrated for Devin Local in Desktop 3.10.67 only**. Read-only, session-scoped change detection and one event-level incremental comparison were observed on synthetic sessions. This is not a guarantee of lossless collection under all failures or a validation of other Desktop agents. P1 must resolve the limitations below before claiming a production-ready collector. No task registry, dashboard, or semantic integration is claimed.

## Environment and setup (2026-10-28)

- Personal macOS 26.6.2, Apple Silicon; a fresh checkout of this planning repository. Before installation, `~/Library/Application Support/Devin`, `~/Library/Application Support/Windsurf`, `~/.devin`, and `~/.codeium/windsurf` did not exist. Existence checks only; no company data was examined.
- System Git and Homebrew could not run because the Xcode license had not been accepted. A preinstalled alternate Git successfully cloned the private repository using the existing GitHub login. The license was not accepted on the user's behalf.
- Installed Devin Desktop 3.10.67 in `~/Applications` from the vendor's distribution URL listed in the [Homebrew cask](https://formulae.brew.sh/cask/devin-desktop); the DMG SHA-256 matched the cask, and `codesign --verify --deep --strict` succeeded. Launched the GUI, completed GitHub login and started isolated synthetic Devin Local sessions. No IDE settings were imported and no terminal command was installed.
- The [Desktop Local Agent documentation](https://docs.devin.ai/desktop/devin-local) says the Local agent shares a harness with the CLI and exposes hooks. The results below are actual Desktop observations, not an assumption that CLI behavior applies to Desktop.

## Observations: Devin Local in Desktop 3.10.67

The only prompts and workspaces used for these experiments were synthetic. Names, actual identifiers, message bodies, credentials, raw hook payloads, and SQLite snapshots are not committed.

- Three test sessions were started through the Desktop UI in one isolated workspace. All three produced responses. An initial connection warning appeared, but these specific sessions completed. This is not a validation of Cloud, Cascade, or arbitrary ACP agents.
- The Desktop-launched Local agent had an open SQLite database at `~/.local/share/devin/cli/sessions.db` with `-wal` and `-shm` sidecars. That directory and database were created during this fresh installation. Its `sessions` table includes `id`, `working_directory`, `title` and `main_chain_id`. `message_nodes` includes `session_id`, `node_id`, `parent_node_id`, and JSON `chat_message` with fields including `message_id`, `role`, and `content`. This was verified against the synthetic workspace, not inferred from CLI documentation.
- A `role: user` node is not necessarily a literal user submission. In one Gamma test, the node corresponding to the first submitted prompt contained a much longer project-context prefix; other user-role nodes had `is_user_input` unset, while the sampled actual prompt nodes had it set to true. The first input also included `metadata.extensions.chisel/acp-content-blocks` with text and resource blocks: one text block exactly matched the synthetic input. Three later test inputs lacked those blocks and had `content` exactly equal to the synthetic submission. These observations are insufficient to define a safe general parser or assume every `role: user` record is a human message.
- Desktop also created per-ACP-session SQLite files under `~/Library/Application Support/Devin/User/acp-messages/`; the two matching test files had `messages(position, kind, payload)` rows for agent thoughts and replies. Streaming reply text was split across payload chunks. In the sampled ACP files, user prompts were not present in that table, while synthetic user and assistant messages were found in Local's `message_nodes`. Do not treat the ACP table alone as the full transcript.
- Two sessions remained visible after a normal Desktop restart. A before/after comparison found the same session IDs, node IDs, parent IDs, embedded message IDs and payload hashes across 34 and 31 nodes respectively. After one resumed session received another synthetic prompt, 10 existing nodes retained their `(session_id, node_id)`, parent and message IDs but acquired different SQLite `row_id` values. Therefore `row_id` alone is not a safe checkpoint. Repeated embedded `message_id` values also occur in multiple nodes; in one synthetic sample 11 duplicate-ID groups had identical JSON payloads. Their general semantics and uniqueness across sources are not yet established.
- Two forced compactions completed in a synthetic session through Desktop. In one before/after comparison, its session ID remained the same and all 40 previously observed nodes still existed, but the active chain changed from 9 nodes to 7; the old active chain had one user and one assistant node, and the new chain contained seven system nodes. The Desktop timeline still showed prior messages. This single experiment does not prove that historical nodes are always retained. Tracking only `main_chain_id` or only the current chain can miss prior history.
- A workspace-scoped `mode=ro`, `query_only` SQLite diagnostic observed three distinct session pseudonyms and identified one changed session while the other two stayed unchanged after a synthetic prompt. HMAC fingerprints include all observed nodes and the head, so the synthetic test also detects a same-length payload change with unchanged node counts. This is session-level change detection, not a demonstrated complete event diff.
- In a separate before/after event comparison for a resumed synthetic session, `(session_id, node_id)` identified 36 new nodes, no changed or missing nodes, and one of the additions contained the known synthetic user input. This is a single event-level sample, not evidence of complete reconstruction in every case.
- While two synthetic sessions were started nearly together, 161 polling reads completed with no reported errors and detected changes in two distinct sessions; both sessions subsequently displayed complete responses. This was one short run, not a stress test.
- A separate read-only process was killed while holding a SQLite read transaction. The database passed `quick_check`, all three synthetic sessions remained discoverable, and Desktop subsequently completed a new synthetic response. This is one process-crash scenario, not proof against every failure mode.
- One quiet read-only query left the database, WAL and shared-memory file bytewise unchanged. During another observation the shared-memory file changed while the app was active; its cause was not isolated. A SQLite WAL reader can participate in shared-memory coordination and briefly hold read locks, potentially delaying checkpointing. No session database writes were intentionally made, but zero impact on the writer and crash/concurrent-write behavior are not yet established.
- A temporary, non-blocking hook configured **only in the synthetic workspace** fired `SessionStart`, `UserPromptSubmit`, and `Stop` from a Desktop-created Local session. The observed input shapes were respectively `{hook_event_name, source, session_id}`, `{hook_event_name, prompt, session_id, prompt_id}`, and `{hook_event_name, stop_hook_active, last_assistant_message, session_id, prompt_id}`. Values other than event name were not retained; local hashes confirmed the hook session ID matched the Local database session ID. The test hook configuration was subsequently disabled. Other events and other agent types were not tested.
- No transcript JSON-file full rewrite was observed or tested. SQLite WAL changes and node reinsertion were observed; do not extrapolate them to all Desktop versions or other providers.

## Probe tools

- `probe/snapshot.py` is a preliminary filesystem comparison aid, not a session collector. It hashes regular files below an explicitly chosen test root, skips symlinks, and saves no bodies or filenames. Output is aggregate counts only. Detected concurrent file changes or read errors fail the run and preserve the previous snapshot; metadata checks cannot detect every concurrent change. Snapshots contain a root path, salted path hashes, content hashes and sizes, and must stay private and outside the repository. It does not provide a consistent SQLite transaction snapshot or event-level completeness.
- `probe/devin_local.py` inspects the observed Local SQLite schema inside one read transaction, scoped to an explicitly named synthetic workspace. It prints only counts, roles, active-chain health, session pseudonyms and keyed content fingerprints. It does not print or retain bodies, titles, raw IDs, or credentials. A private key file produces stable pseudonyms across runs; without one they are ephemeral. This is an experiment, not an incremental collector. SQLite read locks and shared-memory coordination remain a limitation, and source schema/version validation and large-session performance have not been established.
- The manual experiments used private local database copies containing **synthetic test data** for before/after comparisons; these copies were never added to Git. This is separate from the diagnostics' body-free output.

## Validation

`python3 -m unittest discover -s tests -v`: 7 synthetic tests passed. They cover same-length edits, add/delete and replay, symlink exclusion, private snapshot permissions, incomplete-scan preservation, workspace scoping, duplicate IDs, chain traversal, keyed fingerprint changes, refusal to create a missing database, an exclusive SQLite lock, malformed JSON, and a broken chain. A separate CLI smoke test on a temporary synthetic file passed initial discovery, same-size modification, unchanged replay and source preservation. These fixtures do not establish Devin integration correctness.

## Remaining risks and P1 validation

- Establish lossless event-level incremental comparison across concurrent writes, truncation/rewrite, restart, duplicate IDs, chain branches and compaction; demonstrate atomic checkpoint recovery. A session-level fingerprint alone cannot do this.
- Verify how actual user input is delimited from injected project context and how to distinguish internal user-role messages across versions and modes; do not parse undocumented wrappers by assumption.
- Measure source lock/sidecar effects and observer crash behavior while Devin writes; test SQLite busy/locking and malformed or partial data. Never treat an incomplete snapshot as current.
- Establish whether JSON transcript rewrite exists in the relevant Desktop providers, test other supported agents and multiple actively changing sessions, and verify additional hook payloads if needed.
- Avoid claiming broad Desktop coverage from this single Local version. P2–P5 remain unstarted.
