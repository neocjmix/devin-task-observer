## 기준선과 범위

시작 기준선은 `65420919b11b75acc2f8eae630b7ee0ddb02a3ba`의 M3-S01이다.
[상태 트랜잭션 계약](../STATE_TRANSACTION_CONTRACT_2026-10-30_KO.md)의 파일 원본·출처·
고정값 보호를 유지하면서 기존 Observer SQLite 태스크를 새 전용 파일 저장소로 옮긴다.

이관은 로컬의 명시적 일회성 작업이다. 기존 DB를 읽기 전용으로 열고 SQLite backup API로
일관된 사본을 만든다. Devin 원본 DB는 입력으로 허용하지 않는다. 새 파일 상태는 이후의
협조형 보고 원본이며 기존 DB와 상태를 양방향 동기화하지 않는다. 기존 DB·설정은 자동으로
수정하거나 지우지 않는다. 원본 데이터 사용 범위는 개인 환경이어야 하며 회사 데이터가
섞인 DB를 입력하지 않는다. 선택한 태스크의 파일 이관 외에 **복원용 전체 Observer DB 사본**도
로컬에 보존하므로 이 선택은 개인정보 제거 필터가 아니다.

## 보존과 변환

| 기존 정보 | 새 경로 |
|---|---|
| 태스크 ID·제목 | 같은 ID·제목을 가진 파일 태스크. 새 저장소의 revision은 1에서 시작 |
| 설명·lifecycle·생성 시각·이전 revision | 명시적 `legacy` 메타데이터. 새 보고의 상태로 추측하지 않음 |
| 활성 세션 연결 | 새 contributions에 같은 세션 ID로 연결. 보고는 OFF로 시작 |
| 보관한 세션 연결·기여 역할·범위·이력 | 원본 행 보존. 보관된 연결을 자동 활성화하지 않음 |
| 자유 View 구조·섹션·순서·항목·출처·근거 | `legacy.view`에 기존 View 구조를 그대로 보존하고 메뉴에서 가져온 스냅샷으로 표시 |
| 인간 작성 View 내용 | notes에도 보존. 보고가 notes를 덮어쓰지 못함 |
| View 항목·M2 추적 항목 | 같은 항목 ID의 현재 항목으로 투영. 기존 pin 유지. 작성자를 추측하지 않고 `legacy`, 검증 구분은 `legacy_import` |
| 자원·확인 위치 | 이전 값과 ID를 `legacy.resources`, `legacy.review_cursors`에 보존. 확인 위치는 태스크별 독립적으로 유지 |
| 의미 분석 이력·보류 제안·실행 내역·이전 항목·기여·자원 수정 이력 | 태스크별 원본 행 archive와 복원용 SQLite 사본에 보존 |
| 수집 체크포인트·관측 이벤트 | 기존 SQLite 수집 경로 유지. 이관 과정이 관측 수집 위치를 전진시키지 않음 |

View 구조는 가져온 시점의 스냅샷이다. 현재 보고값이 갱신돼도 원본 View를 조용히 재작성하지
않는다. 고정하지 않은 현재 항목은 새 유효 보고로 갱신할 수 있고, 이전 내용은 archive와 파일
이력에 남는다. 고정값은 새 보고의 변경·보관을 거절한다. 현재 항목의 출처가 실제 세션 보고로
갱신되면 새 보고의 출처로 표시한다. 이전 분석 결과를 새 세션이 검증한 사실로 승격하지 않는다.

보관한 세션의 근거처럼 현재 활성 연결에 맞지 않는 원본 근거는 archive/View에 그대로
보존한다. 새 활성 항목의 근거 목록에는 활성 연결에 맞는 참조만 투영한다. 이 변환 때문에
원본 증거가 삭제되는 것은 아니며, 전체 원본 행을 확인할 수 있다.

## 실행 계약과 파일 배치

실제 진입점은 다음과 같다. 아래 경로는 설명용이며 agent가 직접 설정·실행한다.

```sh
./observerctl migrate plan --source /personal/observer.sqlite3 --all
./observerctl migrate apply --source /personal/observer.sqlite3 --all \
  --target /personal/observer-state-m3 --expected-fingerprint PLAN_FINGERPRINT
./observerctl migrate check --target /personal/observer-state-m3
./observerctl migrate rollback --target /personal/observer-state-m3 \
  --restore-to /personal/observer-restored.sqlite3
```

- `--all` 또는 하나 이상의 `--task TASK_ID`가 반드시 필요하다. 암묵적으로 전체 태스크를 선택하지 않는다.
- `plan`은 새 태스크 스키마까지 검증하고 태스크별 개수·제약·fingerprint를 반환한다. 실제 저장소를 만들지 않는다.
- 알려진 Devin 원본 저장 디렉터리 `~/.local/share/devin` 아래의 이관·복원 출력은 심볼릭 링크 별칭을 포함해 거절한다.
- `apply`는 **존재하지 않는 새 전용 root**만 생성한다. 기존 파일 태스크와 합치거나 덮어쓰지 않는다.
- 검토한 fingerprint를 전달하면 그 사이 선택 범위의 상태가 바뀐 경우 `source_changed`로 중단한다.
- 동일 source·선택·fingerprint로 성공한 이관을 재요청하면 결과를 재사용한다. 이후 새 보고가 있어도 초기 상태로 덮어쓰지 않는다.
- `check`는 backup/archive의 무결성, 현재 태스크 건강도, 원상복원 가능 여부를 반환한다. 이 결과는 진단 시점의 정보이며 실제 롤백은 락 안에서 다시 검사한다.

```text
observer-state-m3/
  tasks/<same-task-id>/state.json
  tasks/<same-task-id>/history/...
  reports/...
  migration/
    legacy.sqlite
    manifest.json
    manifest.sha256
    archive/<same-task-id>.json
```

전체 DB 사본과 태스크 archive는 로컬 보존 자료이며 Git에 넣지 않는다. manifest에는 원본
경로·선택 범위·fingerprint·파일별 체크섬을 기록한다. 원본 archive는 임의 수정을 감지하는
보존 자료이지 악의적인 같은 사용자 프로세스를 방어하는 보안 경계는 아니다.

## 실패·복원 경계

- staging 디렉터리에서 전부 검증·생성한 뒤 같은 부모 디렉터리 안에서 rename으로 게시한다.
  실패하면 부분 태스크를 정상 저장소로 노출하지 않고 원본 DB를 유지한다.
- 최대 32개 태스크, 태스크당 2 MiB, 트랜잭션 기록 16 MiB, DB backup 128 MiB, 테이블별
  선택 50,000행의 한계를 적용한다. 새 스키마가 표현하지 못하는 내용·큰 문자열·중복 ID 등은
  전체 이관을 거절한다. 잘라서 성공으로 처리하지 않는다.
- 알 수 없는 DB 테이블, 잘못된 참조, 지원하지 않는 구조는 명시적 오류를 반환한다.
- 롤백은 **이관 이후 파일 저장소에 어떤 후속 변경도 없을 때만** 허용한다. 같은 커밋 락에서
  원본 inventory를 비교한다. 새 보고·메모·외부 수정·archive 손상이 있으면 거절한다.
- 롤백은 파일 root를 삭제하지 않는다. `retired` 표식을 남겨 이미 실행 중이던 CLI의 뒤늦은
  읽기·쓰기까지 거절하고, backup을 **새 SQLite 파일**에 복원한다. 기존 source나 기존 복원
  파일을 덮어쓰지 않는다. 파일 상태도 그대로 남아 검토할 수 있다.
- retirement 이후 복원 파일 게시 전에 중단되어도 같은 롤백을 재시도할 수 있다. 중간 상태에서
  새 보고를 다시 허용하지 않는다.
- 롤백은 실행 환경을 자동 전환하지 않는다. 복원 파일 사용 여부와 서비스 root는 별도 실행
  설정이다. 후속 변경이 있는 root에서 이전 DB로 자동 되돌리는 기능은 제공하지 않는다.

## 일상 실행 전환과 남은 제약

메뉴 실행 경로는 새 파일 root를 읽고 기존 SQLite는 결정론적 관측용으로 사용한다. 이관 자체가
예전 웹 UI의 task 변경을 막거나 기존 프로세스를 종료하지는 않는다. 실제 전환에서는 새 root와
메뉴/collector 실행 경로를 명시적으로 선택하고 예전 웹 task writer를 함께 실행하지 않아야 한다.
코어가 구·신 저장소를 동시에 갱신하는 경로는 없다.

이번 범위에서 기존 사용자 DB의 실제 전환, 기존 파일 태스크가 이미 있는 root로의 병합,
대규모 데이터 이관, legacy View 자체의 새 구조 편집, 예전 review cursor를 이용한 새 메뉴의
변경 확인 동작은 완료로 보고하지 않는다. 원본 정보는 조회·복원 가능하게 보존되며 현재 보고와
가져온 스냅샷의 차이를 표시한다. 지원하지 않는 전환을 성공한 것처럼 자동 처리하지 않는다.
