## 현재 범위

M3 협조형 보고와 UI V2는 [기준선](BASELINE.md)의 범위까지 구현됐다. M3-S01–S05와 UI-V2-S0–S8을 다시 미구현 계획으로 취급하지 않는다. 당시 P0–M2 계획은 [보존 원문](history/IMPLEMENTATION_PLAN_P0_M2.md)에 있다.

기본 관측은 LLM 없이, 의미 보고는 작업 세션의 스킬·CLI로 수행한다. 태스크–세션 다대다, 파일 원본, 낙관적 커밋, 명시적 핀·메모·이력 보존, 상태 막대 UI, Python/JS 중심 스택을 유지한다. 상세 계약은 [데이터](DATA_AND_RECONCILIATION.md)와 [트랜잭션](STATE_TRANSACTION_CONTRACT.md)을 따른다.

## 다음 작업 선택

구체적인 남은 작업과 GitHub 이슈는 [백로그](BACKLOG.md)에만 관리한다. 현재 가장 먼저 확인할 항목은 **B01: 상태 경로 이전 후 실제 세션 보고 연속성**이다. B02 개인 실사용 관측은 사용자가 맡기로 한 범위이며 에이전트는 결과 정리와 분석을 담당한다.

이번 정리는 기준선·문서·이슈 관리이며 새 기능 구현을 시작하지 않는다. 우선순위 표는 실행 순서 제안이지 모든 작업의 즉시 착수 승인이 아니다. 기존 세션 제어, 회사 자료 사용, 모델 분석 확대를 다시 기본 경로에 넣지 않는다.

## 슬라이스 진행 규칙

1. [검증·인수인계](VALIDATION_AND_HANDOFF.md)대로 브랜치·변경사항·해당 이슈를 확인한다.
2. [슬라이스 목록](SLICES.md)에 다음 ID를 예약한다. M3의 다음 미사용 번호는 `M3-S06`이며 아직 예약하지 않았다. UI V2 S0–S8의 번호를 재사용하지 않는다.
3. 시작 커밋·포함/제외 범위·완료 조건·예상 승인 필요 사항을 기록한다. 실제 인증·권한 등 필요한 때만 사용자에게 요청한다.
4. 기존 코어를 사용해 최소 구현을 완료하고 적합한 단위·통합·실제 실행 검증을 수행한다. 실패 원인을 수정하고 재검증한다.
5. 실제/합성/Mock/미검증을 구분해 슬라이스에 기록한다. 현재 설명과 백로그·이슈를 함께 갱신한다.
6. 해당 ID의 커밋을 기존 브랜치와 Draft PR에 반영한다. 별도 요청 없이 병합·재배포·자동 실행 등록을 하지 않는다.

## 완료 판정

테스트 수만으로 전체 제품 완성을 선언하지 않는다. 사용자가 태스크를 연결하고 세션 보고를 켠 뒤 출처·시각·오류를 보면서 현재 작업을 이해할 수 있어야 한다. 매 턴 보고나 완전한 의미 정확성은 새 게이트로 추가하지 않는다. 지원하지 않는 기능·환경을 “추후 반드시 구현”으로 바꾸지 않는다.
