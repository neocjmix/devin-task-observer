# 설계 변경안 평가

2026-10-30. 평가 대상은 먼저 커밋·푸시한
[`3407f660c86701dc3c0a6de9e3644843438fbe2e`](https://github.com/neocjmix/devin-task-observer/commit/3407f660c86701dc3c0a6de9e3644843438fbe2e)의
[설계 변경안](DESIGN_CHANGE_PROPOSAL_2026-10-30_KO.md)이다. 현재 구현 기준은 `f20696d`다.
설계 문서와 기존 코드의 책임 경계를 대조했다. 새로운 모델·GUI·능동보고 실험은 하지 않았다.
**아래 권고는 추가로 확정한 설계나 구현 승인이 아니다.**

## 사용자 후속 결정으로 정리된 사항

이 평가는 이전 커밋을 대상으로 한 당시 기록이다. 이후 사용자 결정은
[변경안 0절](DESIGN_CHANGE_PROPOSAL_2026-10-30_KO.md)과
[상태 트랜잭션 계약](STATE_TRANSACTION_CONTRACT_2026-10-30_KO.md)에 반영했다.
충돌하는 아래 권고는 새 착수 조건으로 삼지 않는다.

| 당시 평가 | 후속 결정 |
|---|---|
| R1 보고 충실도 | 실용적 신뢰성을 수용. 매 턴·완전 보고를 강제하지 않음 |
| R2/R3 저장·일관성 | 구현 담당자가 챙김. 읽기–판단–쓰기는 낙관적 락, 최종 버전 확인·쓰기만 원자적으로 처리 |
| R4 인간 수정 보호 | 명시적으로 고정한 추적값만 자동 변경에서 보호. 비고정 값은 사람이 수정했어도 후속 유효 보고로 갱신 가능. 메모·변경 이력은 항상 보존 |
| R5 의미 집계 | 같은 항목은 최신 성공 커밋을 현재 상태로 사용. updated-by와 이력을 남기고 최종 의미 조정은 세션에 맡김 |
| R6 추적 항목 | 각 세션이 스스로 정의. revision 충돌 시 최신 값·작성 세션을 읽고 재판단 |
| R8 비용 | 현재 예측을 수용하고 실전 사용에서 측정·조정. 사전 벤치마크를 새 착수 조건으로 요구하지 않음 |

이 결정이 원자성 검증이나 스키마·범위·인간 정보 보호까지 생략한다는 뜻은 아니다.
현재도 구현 전 플래닝이며 아래는 후속 결정 이전의 평가 원문이다.


## 1. 종합 판단

이 방향은 사용자가 원하는 제품에 더 직접적으로 접근한다. 이미 문맥을 가진 작업 에이전트가
관심 항목의 변경을 보고하고, Observer는 이를 안전하게 기록해 읽기 쉬운 상태로 유지한다.
파일 중심 저장과 익숙한 스택도 사람·에이전트의 접근성과 유지보수에 맞는다.

그러나 **아직 구현에 바로 들어갈 만큼 계약이 닫힌 상태는 아니다.** 가장 큰 미결정은
보고 충실도, 파일 저장의 일관성·복구 단위, 여러 세션의 주장을 태스크 상태로 표현하는 방법이다.
별도 LLM을 제거해도 이 문제가 자동 해결되지는 않는다. 실패가 감춰지면 기존보다 싸지만
믿을 수 없는 상태판이 될 수 있다.

비용 절감 역시 현재는 가설이다. 직접 질의의 cache hit 관측은 유리한 단서지만 능동보고의
지침·도구·출력·추적 계약 재조회·작업 지연을 포함한 실제 비용을 측정한 결과는 아니다.

## 2. 설계의 장점

| 장점 | 실제 가치 | 제한 |
|---|---|---|
| 작업 세션이 의미 판단 | 별도 분석에 문맥을 다시 구성하는 부담을 줄일 수 있음 | compaction·긴 작업·지침 누락의 영향은 남음 |
| 명시적 지속추적 항목 | 에이전트가 무엇을 보고해야 하는지 알 수 있고 누락 평가도 가능 | 사용자가 모든 항목을 수동 설계해야 한다면 초기 설정 부담이 커짐 |
| CLI와 스킬 | 에이전트 종류보다 명확한 로컬 계약을 중심으로 테스트 가능 | 도구 호출만 제공한다고 모델의 보고 준수가 보장되지는 않음 |
| 읽기 전용 기본 관측 유지 | 보고 중단·장애 때도 사실·근거·진단을 계속 제공 | 관측 성공과 의미 상태의 최신성을 분리해야 함 |
| 파일 원본·버전 스키마 | 직접 편집·수정·진단과 에이전트 자체 검증이 쉬워짐 | 교차 파일 일관성·동시 수정·삭제 복구 책임이 새로 생김 |
| 메뉴 막대 View | 브라우저를 찾아 열 필요 없이 관측 상태에 접근 | 많은 태스크·긴 근거·임의 View의 탐색과 편집 범위는 별도 결정 필요 |
| 기존 Python 코어 재사용 | 새 언어로의 전면 재작성과 플랫폼 결합을 줄임 | OS bridge·패키징·업데이트 비용까지 없애주는 선택은 아님 |

## 3. 먼저 닫아야 할 위험

### R1. 보고 활성화와 보고 충실도는 다른 상태다

스킬을 한 번 실행했다고 이후의 모든 변화에서 모델이 CLI를 호출한다고 보장할 수 없다.
작업 중단·compaction·추적 목록 변경·긴 도구 실행에서 누락이 생길 수 있다. 훅 실행 성공도
의미 정보가 빠짐없이 보고됐다는 증거가 아니다.

권고: `활성화 여부`, `마지막 수집`, `마지막 유효 보고`, `보고가 적용한 계약 버전`, `검증 오류`를
분리한다. 보고가 조용하면 변화 없음과 미보고를 구분할 수 없다는 한계를 표시한다.
보고 실패 때문에 Devin의 정상 작업을 차단하지 않으면서, 고장 난 보고를 정상처럼 보이지 않아야 한다.

검증할 것은 ‘스킬 실행 성공’이 아니라 정답 변화가 정해진 합성 시나리오에서 **별도 재촉 없이
얼마나 보고됐는가**, 틀리거나 과도한 보고가 얼마나 생겼는가다.

### R2. 파일을 원본으로 삼으면 원자성과 복구 단위를 다시 정해야 한다

현재 [수집 저장](../observer/store.py)의 관측·checkpoint와
[의미 적용](../observer/reconciliation.py)의 상태·이력·커서는 DB 트랜잭션에 의존한다.
이를 여러 JSON/YAML 파일로 옮기면 단일 파일의 atomic rename만으로 전체 원자성이 유지되지는 않는다.

권고: 엔티티별 원본과 보고 수신의 커밋 경계를 작게 정하고, 중복 없이 재생성할 수 있는
파생 상태를 분리한다. DB와 파일 모두를 원본으로 쓰는 이중 상태는 피한다. 파일당 작은
검증·저장 계약을 먼저 정하고 범용 파일 트랜잭션 엔진으로 확대하지 않는다.

다음 실패를 설명할 수 있어야 한다: 보고 파일은 저장됐지만 projection 갱신 전에 종료,
정의는 바뀌었지만 관계 파일은 아직 이전 상태, 처리 위치만 진행했는데 보고 반영은 실패.

### R3. 내결함성에는 ‘어떤 정상 범위를 계속 쓸지’라는 경계가 필요하다

깨진 항목만 제외하고 나머지를 사용한다는 원칙은 맞지만, 서로 참조하는 항목에 서로 다른
시점의 정상 스냅샷을 섞으면 존재하지 않았던 일관된 상태처럼 보일 수 있다. 스키마 문법이
맞아도 참조·권한·전이 규칙이 틀릴 수 있다.

권고: 파일·엔티티·태스크 중 검증과 복구의 경계를 정한다. 구문 오류와 관계 오류, 편집 중
일시 오류와 지속 오류를 구분하고, 이전 정상 상태와 현재 유효 상태를 명확하게 표시한다.
지원하지 않는 필드를 조용히 지우거나 손상된 파일을 자동 재작성하지 않는다.

### R4. 직접 편집 허용과 인간 정보 보호 사이의 경계를 명확히 해야 한다

CLI의 소유권 검사를 우회해 같은 OS 사용자 권한으로 파일을 직접 수정할 수 있다면,
스키마만으로 ‘에이전트가 인간 정보를 절대로 덮어쓰지 못함’을 보안 수준으로 보장할 수 없다.
정상 스키마의 파일도 잘못된 본문이나 허위 출처를 포함할 수 있다.

권고: 사람·기계 관리 영역과 수정 가능한 파일·필드, 직접 편집의 출처 표기를 정한다.
이전 정상 버전·변경 내역과 충돌 복구는 유지하되, 파일에 적힌 session ID만으로 실제 작성자를
인증하거나 보고를 검증된 사실로 승격하지 않는다. 이는 직접 편집을 금지하자는 뜻이 아니다.

### R5. 세션별 보고가 곧 태스크 전체의 결론은 아니다

A의 구현 완료와 B의 테스트 실패는 동시에 참일 수 있다. A가 자기 블로커를 해결했다는
보고만으로 B가 포함된 태스크 전체 블로커를 해소할 수 없다. 현재
[_apply](../observer/reconciliation.py)의 출처·상태 변경 책임도 저장 방식과 무관하게 남는다.

권고: 세션별 주장·scope·근거를 보존하고, 태스크 단위 값의 집계·대체·충돌 계약을 별도로 정한다.
자유로운 추적 항목의 임의 의미를 결정론적 Core가 알아서 해결할 수 있다고 가정하지 않는다.
다른 세션의 보고를 에이전트가 CLI로 읽어 판단할 수는 있지만, 언제 읽고 무엇을 대체할 권한이
있는지 역시 계약이 필요하다.

### R6. 추적 항목 변경은 이미 진행 중인 세션에 저절로 전달되지 않는다

사람이 tracking 파일을 바꾼 뒤 에이전트가 오래된 항목으로 보고하거나, 중단된 항목에 계속
보고할 수 있다. 현재 [관계 변경](../observer/registry.py)의 revision 검사를 재사용할 수 있어도
새로운 추적 계약의 무효화·재조회는 별도로 구현해야 한다.

권고: 계약 버전, 항목의 안정적 ID, 낡은 보고의 거절·보류·재조회 응답, 삭제 후 과거 보고 보존을
정한다. 보고 중단과 추적 항목 삭제, 이력 삭제를 같은 동작으로 묶지 않는다.

### R7. 메뉴 막대와 스택 선택은 작은 실증으로 결정해야 한다

메뉴 막대에 관측 요약을 띄우는 일과 임의 Persistent View·긴 근거·편집까지 제공하는 일은
범위가 다르다. Python/JS 우선이라는 원칙은 맞지만 특정 bridge의 지원·배포가 확인되기 전에
Swift가 전혀 필요 없다고 보장하지 않는다.

권고: 한 아이콘과 드롭다운에서 실제 저장 상태·오류·태스크 상세를 읽는 최소 프로브로
메뉴 수명·UI 반응·데몬 재시작·패키징을 확인한다. 코어를 옮기지 않고 OS 연결 부분을 제한한다.
프레임워크 선정이나 UI 꾸미기를 보고 신뢰성보다 앞세우지 않는다.

### R8. 데몬 0토큰과 전체 작업의 저비용은 별도로 측정해야 한다

보고가 너무 잦거나 큰 View를 매번 읽으면 기존 세션의 입력·출력과 도구 호출이 늘어난다.
정상 보고를 보장하려고 추가 모델 호출·강제 재시도를 넣으면 새 방향의 비용·비간섭 목표와 충돌한다.

권고: 같은 작업의 보고 off/on 비교에서 전체 토큰과 유용한 갱신 수, 누락, 작업 지연을 측정한다.
보여줄 수 있는 usage와 보고에만 귀속할 수 없는 토큰을 구분한다. 별도 모델 분석과의 비교도
동일 작업·문맥·갱신 빈도로 해야 한다. 작은 직접 질의 실험을 제품의 비용 절감률로 쓰지 않는다.

## 4. 기존 구현을 얼마나 재사용할 수 있는가

| 기존 자산 | 재사용할 책임 | 새로 필요한 부분 |
|---|---|---|
| [Devin adapter](../observer/devin_local.py)·수집 로직 | 검증한 source 해석·원본 보호·관측 ID/해시 | 파일 저장 backend와 새 checkpoint 경계. 원본 schema 변경 지원은 여전히 검증 필요 |
| [Task Registry](../observer/registry.py) | 다대다·안정 ID·scope·revision 개념 | 에이전트 진입점·추적 정의·세션 등록과 직접 편집 검증 |
| [Persistent View](../observer/views.py) | 인간 소유권·핀·이력·자유 구조 보호 | 파일 표현·Markdown 편집과 구조화 상태의 연결 |
| [의미 상태 Core](../observer/reconciliation.py) | 출처·중복·충돌·버전·reported 구분 | 에이전트 보고 수신과 적용 계약. 기존 모델 패치를 그대로 신뢰 입력으로 바꾸면 안 됨 |
| [실행 진입점](../observer/app.py) | 설정·프로세스·복구·선택적 자동 실행의 경험 | 에이전트 CLI·보고 활성화 상태·메뉴 client와 실행 역할 분리 |
| 기존 웹 UI와 모델 어댑터 | 과거 검증 증거·비교 기준 | 보존·정리 여부 결정. 새 핵심 경로로 자동 연결하지 않음 |

Python의 업무 규칙과 검증 경험은 많이 재사용할 수 있지만, 저장 부분은 SQL에 결합돼 있다.
이는 전면 재작성 이유도, 파일 전환이 단순 export라는 뜻도 아니다. 저장 경계만 필요한 범위에서
분리하고 기존 회귀 사례를 유지하는 접근이 적절하다.

## 5. 다음 설계 라운드에서 정할 다섯 가지

1. **보고 계약:** 세션·태스크·항목 ID, scope, 계약 버전, 근거, idempotency, supersede의 의미.
2. **파일 계약:** 엔티티별 원본, 직접 편집 권한·출처, 수신 커밋·재처리·동시 수정·마지막 정상 상태.
3. **신선도 계약:** 관측/보고/계약/검증 상태를 분리하고, 조용한 세션과 보고 실패를 어떻게 표현할지.
4. **태스크 집계 계약:** 여러 세션의 보고를 보존·표현·대체·충돌 해결하는 범위와 책임.
5. **최소 제품 범위:** 메뉴 막대에서 조회·설정·편집을 어디까지 제공하고 훅을 어느 범위에 사용할지.

이 다섯 계약과 작은 정답 시나리오를 정한 뒤, 최소 파일·CLI와 실제 능동보고 프로브를
검증하는 순서가 적절하다. 기존 데이터 마이그레이션과 UI 확대는 그 뒤에 다룬다.

## 6. 향후 검증에서 반드시 실패를 드러낼 사례

| 사례 | 확인할 결과 |
|---|---|
| A 구현 완료·B 테스트 실패 | 두 주장이 출처와 함께 남고 태스크 완료로 잘못 합쳐지지 않음 |
| 한 세션이 두 태스크에 참여 | 보고·추적 항목·읽은 상태가 다른 태스크로 섞이지 않음 |
| 보고를 켠 뒤 지시 없이 상태 변경 | 실제 모델의 보고 여부·누락·토큰 측정. Core mock 성공과 구분 |
| 추적 항목 변경·삭제·보고 중단 | 낡은 보고를 최신 정상 상태로 처리하지 않고 이력 보존 |
| compaction·세션 재개·비정상 종료 | 보고 활성화와 계약 신선도·불확실성이 정직하게 표시 |
| 직접 편집 중 구문 오류·참조 오류 | 원문·오류 표시, 정상 태스크 계속 작동, 이전 상태는 이전임을 표시 |
| 두 프로세스 동시 수정·수신 도중 종료 | 손실·중복·checkpoint 선행 없이 재처리하거나 명시적 충돌 표시 |
| 지원하지 않는 버전·알 수 없는 필드 | 데이터를 보존하고 지원 범위를 표시, 조용한 재작성 없음 |
| 메뉴·데몬 중단·전송 실패 | UI가 실행/신선도/오류를 구분하고 원래 Devin 작업은 계속 |
| 인간 메모·핀·직접 수정 | 정상 보고·복구·이전 상태 재생성으로 사라지거나 덮어써지지 않음 |

## 7. 이번에 검증한 범위

변경안 커밋이 원격 브랜치와 기존 Draft PR #1에 반영된 것을 확인한 후 이 평가를 작성했다.
문서의 링크·코드 블록·공백 오류와 문서만의 변경 범위를 검사한다. 기존 미커밋
`docs/M2_PROGRESS.md`와 `docs/DESIGN_GAP_AUDIT.md`는 수정하거나 커밋에 포함하지 않는다.

이 작업은 문서화와 설계 평가다. 코드·데몬·훅·스킬·데이터·자동 실행을 변경하지 않고,
모델 호출·새 GUI 실험·런타임 테스트도 하지 않았다. 기존 P0~M2 통과를 새 설계의 검증으로
대신하지 않는다. 결론은 **방향은 유효하나 보고 신뢰성과 파일 일관성 계약을 먼저 닫아야 한다**는 것이다.
