## 현재 계약과 운영 문서

- [데이터와 보고 처리](DATA_AND_RECONCILIATION.md): 저장소·관측·보고·후보·legacy 경계.
- [상태 트랜잭션](STATE_TRANSACTION_CONTRACT.md): OCC·출처·핀·메모·이력·복구.
- [확인 위치](UI_READ_CURSOR_CONTRACT.md): 사용자 확인과 태스크 revision 분리.
- [UI 범위](UI_V2_ROADMAP.md), [화면 명세](UI_V2_SCREEN_SPEC.md): 구현된 화면과 지원하지 않는 동작.
- [검증·인수인계](VALIDATION_AND_HANDOFF.md): 재검증, 증거 분류, 다음 세션의 시작 절차.
- [CLI 참조](slices/M3-S01_CLI.md), [스킬](../skills/observer-reporting/SKILL.md): 실행 계약. CLI 참조는 구현 기록 아래에 위치하지만 실제 옵션은 코드의 `--help`와 함께 확인한다.

`P*_PROGRESS`, `M*_PROGRESS`, 날짜가 붙은 이전 설계 경로는 기존 링크를 위한 짧은 안내문이다. 본문은 `history/`에 한 번만 보관한다. 새 설명이나 백로그를 안내문에 다시 쌓지 않는다. `skills/`는 에이전트 실행 지침, `schemas/`는 검증 가능한 데이터 계약이며 역사 문서 형식을 강요하지 않는다.

## 형식

문서는 H1 하나와 다음 공통 메타데이터로 시작한다.

| 필드 | 작성 규칙 |
|---|---|
| 문서 유형 | 현재 설명 / 계약 / 기준선 / 백로그 / 구현·검증 기록 / 과거 기록 / 이전 경로 안내 |
| 상태 | 구현, 검증, 보류, 역사 기록을 구분; 검증 안 한 것을 완료로 쓰지 않음 |
| 기준 | 고정 커밋·날짜 또는 BASELINE 링크; 날짜는 KST |
| 적용 범위 | 제품 경로·슬라이스·당시 실험 범위 |

현재 문서는 한국어 제목과 설명, 정확한 코드/CLI 식별자를 쓴다. 각 문서의 주제에 맞는 `##` 절을 사용하고 테스트 수·기준 SHA를 여러 곳에서 새 결과처럼 누적하지 않는다. 구현 기록의 기본 절은 **범위와 기준 → 구현 결과 → 검증 결과 → 남은 제약**이다.

긴 과거 원문은 해석을 바꾸지 않도록 `당시 기록` 또는 과거 기록 안내 아래 보존할 수 있다. 원문 언어·수치·소제목과 앵커를 억지로 통일하지 않는다. 짧은 영문 기록은 증거를 보존하는 범위에서 한국어로 정리한다. 역사 기록 안의 현재/다음/미구현은 그 시점의 표현이다.

## 권위와 변경 규칙

1. 사용자 최신 결정과 현재 [트랜잭션](STATE_TRANSACTION_CONTRACT.md)·[데이터](DATA_AND_RECONCILIATION.md) 계약을 우선한다.
2. 구현 여부는 [BASELINE](BASELINE.md)의 고정 코드와 실제 증거로 판정한다. 계획 문서만으로 완료를 주장하지 않는다.
3. 할 일의 상세 상태·완료 조건은 GitHub 이슈, 저장소 탐색용 요약은 [BACKLOG](BACKLOG.md)다. 이슈 변경 시 요약도 갱신한다.
4. 새로운 완료 기록은 새 슬라이스에 쓴다. 과거의 실패·skip·미검증 숫자를 오늘 수치로 덮어쓰지 않는다.
5. 새 기준선은 별도 태그로 만든다. 기존 태그는 이동하지 않는다. 문서 정리 커밋과 제품 코드 기준은 구분한다.

## 문서 점검

`python3 scripts/check_docs.py`로 README와 docs의 상대 링크·제목 앵커를 검사한다. `git diff --check`도 실행한다. checker는 외부 URL의 서비스 상태나 문장 내용의 사실성을 보증하지 않으므로 코드/이슈 정합성은 별도 확인한다.
