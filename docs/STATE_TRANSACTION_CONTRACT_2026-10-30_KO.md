# 상태 트랜잭션과 업데이트 출처 — 설계 계약

2026-10-30. 사용자 후속 결정에 따른 **구현 전 설계**다. 코드·스키마·명령이 이미 구현됐다는 뜻은 아니다.
[설계 변경안](DESIGN_CHANGE_PROPOSAL_2026-10-30_KO.md)의 최신 상태·출처·트랜잭션 계약을 구체화한다.

## 1. 사용자 결정

- 의미 보고의 충실도는 실용적인 수준이면 충분하다. 매 턴 보고와 완전한 의미 정확성을 강제하지 않는다.
- 기본 결정론적 관측은 별개로 계속된다. 보고되지 않은 의미 변화까지 알아낸다고 보장하지 않는다.
- 같은 항목은 마지막으로 성공적으로 커밋된 유효 업데이트를 현재 상태로 사용한다.
- 항목마다 어느 세션이 업데이트했는지 남긴다. 최종적인 의미 조정은 세션이 맡는다.
- **추적값은 명시적으로 고정한 경우에만 자동 변경에서 보호한다.** 사람이 수정했어도 고정하지 않았다면 이후 유효한 에이전트 보고로 갱신할 수 있다. 메모와 변경 이력은 항상 보존한다.
- 각 세션이 자신이 기여하는 태스크에서 무엇을 지속추적할지 스스로 정의한다. 사람이 전체 항목을 먼저 설계할 필요가 없다.
- **읽기 → 판단 → 쓰기 전체는 낙관적 동시성 제어로 다룬다. 판단하는 동안 락을 잡지 않는다.**
- 현재 비용 예상은 수용하고 실사용하면서 측정·조정한다. 사전 비용·충실도 벤치마크를 새 착수 조건으로 요구하지 않는다.

사용자의 초기 락 대기 제안은 마지막의 낙관적 락 결정으로 대체됐다. 구현 담당자가 일관성·
중단 복구를 책임진다. 최신 상태 정책은 버전 검증을 통과한 커밋 사이의 순서 규칙이며,
오래된 상태를 읽은 쓰기를 무조건 최종 승자로 채택한다는 뜻이 아니다.

## 2. 세션이 정의하는 추적 항목과 업데이트 출처

항목은 태스크 안에서 안정적인 ID로 공유한다. 세션은 기존 항목을 재사용하거나 새 항목을
정의할 수 있고 다른 세션도 같은 항목을 갱신할 수 있다. 제목이 같다는 이유로 Core가 자동으로
합치거나 세션별로 무조건 분리하지 않는다. 항목 구성과 의미 조정은 세션이 판단한다.

| 저장할 정보 | 목적 |
|---|---|
| task ID / item ID | 태스크와 추적 항목 식별 |
| created-by session | 항목을 처음 정의한 세션 |
| updated-by session | 현재 값을 마지막으로 갱신한 세션 |
| item revision / commit sequence | 항목 변경과 실제 반영 순서 구분 |
| updated-at | 사람이 읽을 수 있는 마지막 반영 시각 |
| value / status / evidence | 현재 내용·보고 상태·가능한 근거 |
| report ID | 같은 보고 재전송의 중복 방지 |

CLI 조회는 값과 마지막 업데이트 세션·revision을 함께 반환한다. 세션은 자기 보고인지 다른
세션이 쓴 것인지 비교할 수 있고, 예전 값·작성 세션은 이력에서 확인한다. 에이전트가 등록된
세션 ID를 조회할 수 있게 하고 모델이 ID를 임의로 추측하지 않도록 한다.

사람의 직접 편집이나 작성자를 확인할 수 없는 외부 편집은 그에 맞는 출처로 표시한다.
본문이 바뀌었는데 예전 session ID를 그대로 실제 작성자인 것처럼 승계하지 않는다.
session ID나 정상 스키마만으로 내용의 진실성·실제 작성 주체를 인증하지 않는다.

## 3. 낙관적 읽기–판단–커밋

1. **읽기:** CLI가 일관된 현재 상태, 업데이트 세션, 판단에 관련된 상태·추적 정의의 revision을 반환한다.
2. **판단:** 에이전트는 락 없이 판단한다. 이 시간에 다른 세션의 작업과 업데이트는 계속된다.
3. **조건부 커밋:** 이번 변경과 읽었던 revision을 제출한다. Core가 버전 확인과 상태 반영을 한 원자적 구간에서 수행한다.
4. **일치:** 스키마·참조·태스크 범위·보호 규칙을 검증한 유효한 변경을 저장하고, 값·updated-by·revision·이력을 함께 갱신한다.
5. **불일치:** 쓰지 않고 `revision_conflict`와 최신 값·revision·업데이트 세션을 반환한다. 세션이 다시 읽고 판단해 후속 보고한다.

예: A가 revision 12를 읽고 판단하는 사이 B가 13을 커밋하면, A의 expected revision 12 쓰기는
반영하지 않는다. A는 B의 최신 값과 작성 세션을 확인하고 유지·수정·대체 여부를 판단한다.
그 후 새 판단이 버전 검증을 통과해 커밋되면 그것이 최신 상태가 된다.

Core는 버전 충돌을 검사하지만 의미를 해석해 조정하지 않는다. 오래된 보고를 조용히 재적용하거나
새 모델을 호출해 자동 재판단하지 않는다. 서로 다른 항목은 항목별 변경으로 보존한다.
사람의 메모·핀·확인 위치 등 보호 영역은 자동 보고의 변경 대상 밖에서 유지한다.

### 추적값의 명시적 고정

사용자는 ‘명시적으로 고정한 값만 보호’를 선택했다. 추적값을 사람이 수정했다는 이유만으로
영구적인 인간 소유·자동 변경 금지 상태로 전환하지 않는다. 고정하지 않은 값은 최신 유효
보고로 갱신하고, 이전의 인간 수정 내용과 작성 출처는 이력에 남긴다.

값 고정은 에이전트 보고가 해당 값·상태를 변경하지 못하게 하는 명시적 상태다. 보고가 고정을
스스로 해제하거나 같은 항목을 삭제·대체해 보호를 우회하면 안 된다. 고정과 해제는 관련
revision에 반영해, 읽은 뒤 고정이 바뀐 쓰기도 낙관적 검증에서 감지한다.

고정한 값의 변경 시도는 구체적인 보호 오류로 응답한다. 메모·확인 위치·변경 이력 등 별도
사용자 정보는 추적값의 고정 여부와 관계없이 자동 보고로 덮어쓰거나 삭제하지 않는다.

revision 검사 범위는 판단이 읽은 관련 항목·추적 정의를 포함하도록 설계한다. 단순한 수집 시각처럼
무관한 정보 변화까지 섞어 충돌을 남발하지 않는다. 정확한 토큰·검사 단위는 구현 시 작게 정한다.
최신 순서는 세션이 주장한 시각이 아니라 저장 측에서 부여한 성공 커밋 순서로 판단한다.

## 4. 버전 확인과 파일 반영의 원자성

버전을 비교한 뒤 다른 프로세스가 끼어들 수 있는 상태에서 파일만 쓰는 방식은 충분하지 않다.
초기 구현은 **매우 짧은 공통 커밋용 파일 락**으로 compare-and-commit을 묶는다. 일관된 조회도
동일한 커밋 경계를 따른다. 안정적인 별도 lock 파일을 사용하고 교체되는 상태 파일 자체를 잠그지 않는다.

이 내부 락은 LLM의 읽기–판단–쓰기 전체를 잠그는 비관적 락이 아니다. 락 안에서는 최신 커밋
확인·revision 비교·검증·저장만 수행하고, LLM·네트워크·사용자 응답을 기다리지 않는다.
대기가 길어지면 유한한 timeout과 명확한 busy 결과를 제공해 UI와 원래 작업을 막지 않는다.

단일 파일은 임시 저장·내구성 확인·원자적 교체를 사용한다. 여러 파일의 현재 값·출처·이력·처리
기록·checkpoint가 함께 바뀌는 경우에는 작은 로컬 트랜잭션 기록과 중단 복구가 필요하다.
락과 단일 파일 rename만으로 여러 파일의 crash 원자성이 완성됐다고 설명하지 않는다.

구현 담당자는 영향 파일의 이전·이후 상태와 transaction/report ID를 준비 기록에 남기고,
읽기·쓰기 전에 미완료 커밋을 복구하도록 작게 설계한다. 복구 불가한 영향 범위는 이전 정상 상태
또는 사용 불가와 오류를 표시하고 원문을 보존한다. 무관한 정상 범위는 가능한 한 계속 제공한다.
범용 파일 DB나 대규모 트랜잭션 프레임워크를 만드는 범위는 아니다.

성공 응답 전 종료로 결과가 불확실하면 동일 report ID 재전송으로 이미 반영됐는지 확인한다.
같은 성공 보고를 재적용해 revision을 다시 올리거나 최신 작성자를 바꾸지 않는다.

## 5. 직접 편집의 지원 범위

사람·에이전트의 직접 편집은 계속 지원한다. 안전한 편집 helper는 읽은 작업 사본·revision을
제공하고 반영 시 같은 조건부 커밋 경로를 따른다. 편집·판단 시간에 커밋 락을 점유하지 않는다.

규약 밖의 임의 편집까지 낙관적 트랜잭션을 지켰다고 가정하지 않는다. 이런 수정도 원문을
보존하고 감지·검증하되 외부 편집 또는 오류로 표시한다. 미완료 커밋·다른 수정과 충돌하면
조용히 덮어쓰지 않는다. 파일이 깨져도 정상인 다른 태스크와 진단은 가능한 한 계속 제공한다.

정확한 helper 명령·파일 배치·기록 포맷·flush 순서·복구 절차는 아직 구현하지 않았다.
원자성 보장의 범위를 CLI·데몬·UI와 안전한 편집 경로에서 일관되게 검증해야 한다.

## 6. 구현 시 확인할 것

- A 읽기 → B 커밋 → A 커밋 시도에서 A가 거절되고 B의 값·revision·작성 세션을 확인할 수 있다.
- 판단 중 락이 없고, 버전 확인부터 쓰기까지는 다른 커밋이 끼어들지 않는다.
- 값·updated-by·revision·이력·처리 위치가 함께 반영되고 같은 report 재전송이 중복되지 않는다.
- 사람이 수정한 비고정 값은 후속 유효 보고로 갱신되면서 이전 내용이 이력에 남고, 고정 값은 거절된다. 읽기 후 고정 변경도 revision 충돌로 감지한다.
- 여러 파일 반영 도중·성공 응답 전 종료와 복구·재시도에서 부분 상태를 정상으로 노출하지 않는다.
- 각 세션이 추적 항목을 정의·재사용하고 다른 세션의 최신 보고를 읽어 후속 보고로 조정한다.
- 매 턴 보고·완전한 의미 합의·비용 사전 증명을 요구하지 않고 실제 사용에서 누락·비용을 조정한다.

위 내용은 설계 계약이며 작동 검증 완료를 뜻하지 않는다. 현재 단계는 계속 플래닝이다.
